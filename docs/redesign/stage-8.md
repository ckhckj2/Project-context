# 8단계 — 통합 검수와 배포 준비

2026-09-23. 로컬 통합 검수와 배포 산출물 검증 완료. GitHub 업로드·원격 CI 활성화·실제 사이트 반영은 완료하지 않았다.

## 이번 결과

- 홈 → 업무 선택 → 첫 저장 → 체크 유지 → 분야별 승급 → 설명 깊이 선택 → 새로고침 복구를 배포 파일만으로 연속 검증했다.
- 기존 프로젝트·통합 성적·상세 정보가 남아 있으므로 옛 렌더러를 일괄 삭제하지 않았다. 새 앱을 기본 진입점으로 하고 기존 화면을 `legacy.html`에 보존하는 호환 배포를 구성했다. 전체 콘텐츠 이전과 기존 기록 이전이 검증되기 전 호환 화면을 제거하면 안 된다.
- 소스 저장소의 기존 `index.html`과 기존 기록 키는 그대로다. 배포 시 생성한 루트 안내 페이지가 새 앱으로 이동시키고, 기존 `?entry=projects|quiz|task` 링크는 검증된 호환 화면으로 이동시킨다. 임의 외부 목적지를 받지 않는다.
- 테스트·개발 도구·시안·스크린샷·문서·패키지·저장소 메타데이터는 배포 폴더에 포함하지 않는다.

## 배포 구성

| 명령 | 산출물 | 용도 |
| --- | --- | --- |
| `npm run build:site` | `dist/` | 기존 운영 화면, 호환/되돌리기 검토용 |
| `npm run build:release` | `dist-release/` | 새 앱을 기본으로 하는 배포 후보, 122개 파일 |
| `npm run check` | 검사 결과 | 기반 34개 + 기존 검사 27개, 포맷·경계·CSP |
| `npm run check:browser` | 브라우저 검사 결과 | 기존 전체 흐름, 새 앱 각 단계, 최종 배포본 |

새 파일 `app/release.html`, `app/release-entry.mjs`는 배포 진입점이다. 빌더는 검토된 HTML 자산과 정적 모듈 의존성만 추적한다. 모듈 원문을 임의로 재작성하거나 기존 HTML을 덮어쓰지 않는다. `/Project-context/`처럼 하위 경로에 배포한 상태를 검사했다.

GitHub Actions의 수동 Pages 배포는 `Validate` 성공 후 `dist-release/`를 다시 만들어 배포하도록 변경했다. Pages Source가 GitHub Actions인지 확인하는 기존 차단 조건을 유지했다. 저장소 설정과 원격 필수 검사 활성화는 아직 확인·변경하지 않았으므로 원격에서 강제된다고 표시하지 않는다.

## 운영 반영 상태와 차단 사유

원격 main은 조회 당시 `5d4cdee40571a04eb14c543e6e5291c26dd27a9d`였고, 새 단계의 코드는 로컬 커밋에 있다. GitHub 전송 가능성을 확인하려던 `git push --dry-run`은 자동 승인 검토에서 차단됐다. 사유는 로컬 8단계 검수 승인과 공개 GitHub 저장소로 코드를 보내는 승인을 구분해야 한다는 것이었다. 다른 API나 간접 실행으로 우회하지 않았다.

사용자가 `ckhckj2/Project-context` 업로드·배포를 명시적으로 승인하면:

1. 원격 변경과 게시 경로를 다시 확인하고 현재 검증 커밋을 검토 가능한 브랜치로 올린다.
2. 원격 Validate 결과를 확인한다. Pages Source·필수 검사·배포 권한을 확인하고 필요한 설정만 적용한다.
3. 검증된 커밋을 반영하고 수동 Pages 배포를 실행한다.
4. 실제 주소의 새 화면, 자산, 기존 정보 접근과 저장 복구를 다시 확인한 뒤 운영 반영 완료를 보고한다.

실패하면 운영 전환 성공으로 표시하지 않는다. 기존 운영 빌드(`npm run build:site`)를 동일한 검증 경로로 재배포하는 방식으로 되돌릴 수 있다. 기존 및 새 저장 키를 삭제하거나 강제 이전하지 않는다. 배포 경로가 달라져도 저장 origin이 같아야 기존 브라우저 기록 접근을 유지할 수 있으며, 도메인 변경은 이번 범위가 아니다.
